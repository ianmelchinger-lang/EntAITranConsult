Place the check

An oversight failure happens when a system performs as specified and a person defers, without noticing, to output that is wrong. A malfunction is different: the system itself misbehaves, and engineers repair it. In a workflow that acts across several steps there is a second problem. A review at the end arrives too late, because an irreversible action may already have happened before anyone saw the input. So verification has to be designed into the sequence: at a named step, held by a named person, with the power to halt the run.

A manufacturer’s customer-exception workflow runs five steps in order. Last month a customer received terms that had since been replaced. The log shows that each step performed as it was built to perform. Once step 4 runs, the customer has the message and nothing recalls it.

  1. Retrieve the terms that apply from the document store.
  2. Classify the request against those terms.
  3. Write the message.
  4. Send the message to the customer.
  5. Update the record to match the decision.

Each card names a check and the job it is meant to do. Place each one where it can still do that job. A check cannot sit before the step that produces what it needs. If a card cannot do its job anywhere in this sequence, choose “Cannot be placed.” Where more than one position works, any of them passes.

Second pass: move the point of no return

Suppose the workflow now holds every written message for a day before step 4 sends it. Nothing else changes. Place the day-end read again, as it now works.
