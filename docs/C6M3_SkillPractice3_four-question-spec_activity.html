Specifying an explanation

Explainability is not a property a model has or lacks. It is a requirement someone specifies, and the specification has four parts: what explanation is required, who receives it, what evidence supports it, and the threshold below which an output cannot support the action it is being asked to support. Because audiences ask different questions, each audience needs its own specification. For some deployments the requirement is a legal obligation and not a preference.

A manufacturer is extending an automated maintenance-scheduling system from two plants to seven. Its executive committee has asked for one thing about it, and the advisor has to turn that request into something a team could build to.

The client’s request

“The scheduling system must be explainable.”

What the governance record holds

No deviation threshold is defined that would trigger a review of the system’s output, and no one is named to receive an alert if the output deviates.

What the plan holds
